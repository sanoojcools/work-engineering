Also true, not a per-attribute row:

- Container `GenomeImportRequest` is `extra="ignore"` — benign top-level metadata (`source_files`, `automation_index`, a stray `org`) does not 422; GQS scores it instead.
- GQS runs on the raw dict, before Pydantic validation.
- `dual_scoring_kappa` is caller-supplied. No mechanism produces two independent scores to compute it from.
- No file writer exists yet for `UploadedFile` — no endpoint uploads a file, so `hash_sha256` in provenance today is whatever the caller supplied, never server-computed.
- Slice 3 PR 3a: `work_units`, `spec`, and `census` are off the legacy global `spec_api_key` (default `dev-spec-key-change-me` is gone, not just changed) and onto per-org `X-Spec-Key` / RLS, same as genome and files. `POST /api/org/keys/rotate` rotates a key; the old one 401s after a 60-minute grace window (`dependencies.ROTATION_GRACE_MINUTES`). `ontology`, `discovery`, `projections`, `verdict`, `work-graph`, `economics`, `regulatory`, `verification`, `clients`, and `admin` are still unauthenticated `DbDep` routes — that's out of PR 3a's scope (playbook G.1 names work_units/spec/census only), not a gap this PR closed.
- Slice 3 PR 3c: `consent_receipts` (P0 foundation table, RLS since alembic `9a07306c5434`) now has its first HTTP surface — `POST/GET /api/consent/receipts`, `POST /api/consent/receipts/{id}/revoke`, per-org `X-Spec-Key`, same RLS isolation as work_units. `purge_expired_consents()` (daily sweep, triggered manually today via `POST /api/admin/consent/purge`) tombstones `status=active` receipts past `expires_at`. **This reports 0 purged in any real environment today** — no caller writes a consent receipt from an actual interview/transcript flow yet (`genome_import.py` still hardcodes `consent_receipt_id=None`); the only way to see `purged: 1` is the test suite's direct-DB backdated fixture. The job and its RLS-bypassing cross-tenant scan are proven correct; the upstream wiring that would make it matter in production (genome import creating a real receipt at interview time) is not built.
- 15 No-Cracks Gates: #15 (RLS) is fully live. ~6 are partially live. ~8 are specified-only. GQS ≥ 90 means the quality gate passed — it does not mean 15/15 gates passed.
- **Scout Elevated V2 PR1** (`scout_interview_sessions` / `scout_captured_units`, `routers/scout.py`): a founder/SME interview session, a live-editable Work Capture Grid, and a Genome Strength completeness meter are real — tenant-scoped via `X-Spec-Key`/RLS, browser-tested end to end (session create → 401 → key banner → retry → add row → live meter update → inline edit → persisted). None of the "adaptive AI follow-up" or "words become structure live" behavior the design doc describes runs on an LLM — `LLM_PROVIDER=none` in this environment. `DiscoveryPartner`'s question bank is a static, hand-written list per track (founder/SME), not AI-generated or AI-adaptive; its voice input is the browser's own `SpeechRecognition` API (dictation only, works with no backend LLM, degrades to typing where unsupported) — it is not an AI interviewer. Completeness is computed from structured fields the interviewer/interviewee types or dictates into the grid directly; nothing extracts structure from free-text notes automatically. The design doc's `org_id` naming was corrected to `client_id` throughout (this repo's actual tenant column — see `SCOUT_OPERATING_PLAYBOOK.md` §A.3, "never introduce an `orgs` table").
- **Scout Elevated V2 PR2-4** (all 5 elevations, `services/scout_timeline.py` / `scout_contradictions.py` / `scout_pain.py` / `scout_story.py` / `scout_future.py` / `scout_genome.py`): all real, all browser-verified (see `docs/API.md`'s elevation-by-elevation table for the mechanism each one actually uses). None call an LLM. Two are deterministic arithmetic/scheduling (Time-Travel Replay, Pain Heatmap's automation-potential share), one is a plain text diff with a fixed confidence (Contradiction Resolver), one is a sentence-splitter with a guardrail, not extraction (Story to Structure), and one (Future Preview's "Generate V8 Work Units") is a best-effort mapping onto the real 18-attribute contract via the **existing** `genome_import.import_genome` — several attributes the capture grid never asks for (`trigger`, `actor_constraints`, `acceptance_criteria`, `evidence_required`, `failure_semantics`) get one honest literal placeholder rather than fabricated content, so a thin session's genome correctly scores low and gets blocked by the same GQS gate every other import goes through (verified: a 1-unit session scores GQS 30, `accepted: false` — not silently waved through for being Scout-sourced). Future Preview's UI intentionally has no confetti animation, unlike the design doc's spec — a deliberate call to match the app's existing minimal-motion style, stated in the UI copy itself rather than silently dropped. `scout_pain_signals` (the design doc's optional table) was not created — pain is derived on read from `scout_captured_units`, no new table needed.

- **Stitching Scout to V8 delivery** (`frontend/src/pages/Genome.tsx`, new route `/genome/:versionId`): the missing other half of the demo loop — a real UI over the existing, already-tested `genome.py` router (GQS header, L1 business-object list, L2 work-unit table, L3 full 18-attribute detail, ratify whole-version and ratify-one-business-object, Automation Index tab with bottleneck view and work-graph edge counts). Nothing new on the backend; this page calls endpoints that were already live and tested. `FuturePreview.tsx`'s "Generate V8 Work Units" result now links to `/genome/{version_id}` for both outcomes, gate-passed and gate-failed, closing the Scout → Genome loop visually. **Important, browser-verified finding, not a bug:** the GQS formula (`gqs.py`, frozen) weights `Observed%` at 40% of the score, and every Scout-sourced work unit is honestly labeled `provenance.source_type: "declared"` (interview-derived, not document-derived) — so `Observed%` is structurally 0 for any Scout-only genome, capping its GQS well under the 90 gate. Verified live: an 8-unit, 100%-complete Scout session generates genome v307 at GQS 30.0, "gates passed: none" — and because `import_genome` only persists `WorkUnit` rows on gate pass, that version's Business Objects (L1) list and Automation Index are both correctly empty; the new Genome page renders that empty state honestly rather than erroring or fabricating rows. A genome imported from real observed data (the existing `Private-Genome-MVP-HR-Ops-FIXED.json` fixture) passes the same page's full loop end to end — GQS 94.3, ratify whole version, ratify one business object, drill L1→L2→L3, Automation Index with real bottleneck/hours data — verified live at version v306. Nobody worked around the gate to make the Scout path "look" done; the demo narrative is: Scout gets you a structured, honestly-labeled draft, and V8's own quality gate is what tells you it still needs document-backed verification before it ratifies.

- **Demo-readiness pass** (bugs found by running the demo end to end, not by the test suite — each was reachable in the documented demo path):
  - `POST /api/genome/import` rejected a re-import with a bare 500. `work_units` is UNIQUE on `(client_id, code)` and nothing checked it before the insert loop, so a colliding id blew up mid-loop on a raw `UniqueViolation` — and left the rows written before the collision behind, attached to a version row still claiming the full count, which then collided with every retry. Now a pre-pass violation (`work_unit_id_already_exists`, `duplicate_work_unit_id`) like file provenance already was, and the write phase is one rollback boundary. Covered by `tests/test_genome_import_conflicts.py`, verified to fail against the previous code.
  - `samples/Private-Genome-MVP-HR-Ops-FIXED.json` and the Client A HR seed both define `WU-OFF-03` and `WU-OFF-04`, so the sample could never be imported into Client A. They are two genomes for two employers; `POST /api/demo/bootstrap` now provisions a separate **Sample Genome Co** tenant for the sample rather than reconciling the ids.
  - `POST /api/demo/bootstrap` (new, gated by `settings.demo_bootstrap_enabled`) seeds the demo **and mints first API keys**, returning each plaintext once. `routers/org.py` could only ROTATE a key you already held, so there was no way to obtain a first key through the app — standing up a demo required a hand-written `org_api_keys` INSERT with a manually computed sha256. It hands out a credential over an unauthenticated request, so it must be disabled outside a throwaway local database.
  - `GET /api/genome/versions` (new): every other genome route needs a `version_id` the caller had to already know, so an imported genome was unreachable from the UI. Backs the new `/genome` index page; Genome also had no nav entry at all.
  - `GET /api/org/whoami` (new): nothing exposed which tenant a key belonged to. The company switcher defaulted to Catalog while the key was Client A's, so every tenant-scoped read was correctly filtered to nothing and the UI rendered a screen of zeros with no explanation. The switcher now defaults to the key's own company and says so when they diverge.
  - `GET /api/clients/` counted work units per client on the RLS-bound session, so every count came back 0 — the switcher read "Client A (0)" on a fully seeded tenant. Enumerating tenants is cross-tenant by definition and now uses the system session.
  - `useApi` never sent `X-Spec-Key`, so Overview, Discovery and Economics all 401'd on `/work-units/` (moved to per-org auth in Slice 3 PR 3a) and silently rendered 0.
  - `/demo/prepare` called `SystemSessionLocal()` directly, escaping the FastAPI dependency override — its test was asserting against the developer's real Postgres rather than its own fixture. The cross-tenant session is now an injectable `get_system_db` that `conftest` overrides.
  - `ApiKeyBanner`'s "Save & retry" stored the key and hid the banner **without retrying**, leaving the operator on an unchanged form with nothing to indicate progress. It now awaits a real retry.
  - `routers/org.py::rotate_key` refreshed a row after `commit()` without re-applying the tenant binding — the documented RLS/connection-pool bug this repo already fixes with `_rebind_tenant` in `scout.py`.
  - UI: the stylesheet was reworked around a real type scale, three line weights and a restrained elevation set; nav is grouped rather than eleven equal-weight links; empty and loading states are explicit everywhere they were blank or a bare "Loading…". No behaviour claims changed — a gate-blocked genome now *says* it was gate-blocked and that no work units were written, instead of rendering an unexplained empty page.

- **Story to Structure now really extracts — when a model is configured.** This supersedes the "None call an LLM" claim in the PR2-4 row above, which was true when written. With `LLM_PROVIDER=anthropic` and a key, `services/scout_story.py` calls Claude (`services/llm.py`, official `anthropic` SDK, default `claude-opus-5`) and returns candidate work units with the grid's structured fields filled in. Three things stay true regardless:
  - **The verbatim guarantee is enforced, not trusted.** Every span the model returns is checked against the transcript and *discarded* if it is not a literal substring. A model that paraphrases cannot put words in the interviewee's mouth. Covered by `tests/test_scout_story_llm.py`, including the paraphrase case.
  - **The structured fields are labelled as the model's reading, not quotes**, and a field the transcript does not cover comes back empty and renders as "not stated" — the UI never fills a gap with something plausible.
  - **With no model configured (still the default) nothing changed**: the deterministic sentence-splitter runs and says so, naming `LLM_PROVIDER=none`. A configured-but-failing model falls back to the same splitter and reports the failure rather than looking like the deterministic mode.
  `services/discovery.py`'s candidate suggestion moved onto the same shared client; its hand-rolled Anthropic POST is gone, so the codebase no longer has two ways of calling a model. The other four elevations are unchanged and still call no model. **Tests never call one** — `tests/conftest.py` forces `LLM_PROVIDER=none` for the whole suite, because a developer with a key in their `.env` was otherwise turning `pytest` into live, billed network calls.
- **Demo setup is a button, not a runbook.** `components/DemoSetup.tsx` on Overview calls `POST /api/demo/bootstrap`, stores the returned key itself, and signs the browser in — the terminal step and the copy-pasting of two opaque 32-character keys are gone. It holds both demo tenants' keys locally so switching between Client A and Sample Genome Co is one click. It requests fresh keys automatically when this browser is not already holding a usable one, because a key's plaintext exists only at the moment it is minted and a re-run would otherwise leave you signed out. Everything it does is the same endpoint documented in the README; nothing is faked to make the demo smoother.
- **Work Capture Grid sample rows** (`lib/scoutSamples.ts`): eight HR & People Ops rows — the same function as the Client A census, so a Scout session sits in the same domain as the rest of the screen. They are saved through the same `POST /scout/sessions/{id}/units` a typed row uses, so the completeness meter reflects them exactly as it would hand-typed input. Eight is not arbitrary: the meter expects 8 work units, so the full set takes a session to 100% and unlocks Future Preview.
