# Work Engineering + Scout — Production Engineering Playbook

**Written:** 2026-09-01, by Claude Code, from a full read of this repository's git history (33 commits, 2026-08-20 → 2026-09-01), its living docs, its two frozen business-logic modules, and direct hands-on experience building roughly two-thirds of that history in a single continuous session.

**What this is.** A retrospective of how Work Engineering V8 + Scout actually got built — the real sequence, the real bugs, the real discipline that worked and the discipline that was missing — turned into a prescriptive, phase-by-phase plan for building a next version *well*, from an empty repository, using AI coding tools as the primary builders. It is written to be read cold, without the companion state/reference document open, though the two are designed to be read together.

**What this is not.** Not a retrospective on *product* decisions (whether Work Unit, VERDICT, or GQS are the right abstractions — that's V8's own argument, made at length in `docs/Work-Engineering-V8.md`). This document is about *how the code got built*, not what it says about work.

**A note on evidence.** Every claim below that reads as a fact (a commit hash, a test count, a bug description) is checked against the actual repository, not recalled from memory. Every claim that reads as a recommendation is opinion, and is written as one — this document does not try to launder judgment as fact, in keeping with the project's own honesty discipline (see `docs/HONESTY.md`).

---

## 1. The build, in one paragraph

Between 2026-08-20 and 2026-09-01 — twelve days, 33 commits — this repository went from nothing to a two-sided product: a FastAPI + Postgres + React specification layer (Work Engineering V8: Work Units, VERDICT autonomy scoring, a genome-quality gate, five projections, a Spec API for execution systems to consume) fused with a capture layer (Scout: multi-tenant interview sessions, a live Work Capture Grid, five "elevation" analysis views, and an LLM-optional extraction path) sharing one multi-tenant, row-level-security-isolated Postgres schema and one demo. It happened in two visibly different modes: five days of fast, low-ceremony scaffolding by **Cursor**, then seven days of disciplined, slice-by-slice, test-gated rebuilding by **Claude Code** that corrected foundational bugs the fast phase had shipped and then built the rest of the product on top of a now-provably-sound foundation. Both modes were necessary; neither would have produced this alone. Section 6 covers why.

## 2. The actual build sequence

This is what happened, reconstructed from the commit log itself — not a sanitized version of it. Read it for the *shape* of a well-run incremental build: each entry names what got built, what broke, and what the commit explicitly refused to touch.

### Phase 0 — Cursor prototype (2026-08-20 → 08-25, 4 commits)

`53d5d2d` → `8ea6f25` → `53b8274` → `44af43f`. Turned the V8 written spec into a runnable skeleton: FastAPI + Postgres + React, Work Units, VERDICT gates, economics, a Spec API, a UI. Then three fast follow-ons — a friction-reduced UI journey for one seeded Work Unit, Excel bulk upload, and a single-company demo scope. This phase's job was speed: go from a 1,064-line written argument to something clickable, and it succeeded at that job in five days.

It also shipped, un-flagged at the time, the foundation's two structural weaknesses that the next phase spent its entire first commit correcting: **no Alembic** (schema was `Base.metadata.create_all()` on every boot — destructive model changes needed a fresh volume) and **no real auth** (Spec routes behind one shared secret, everything else open). `ARCHITECTURE.md`, written at the end of this phase, states both as deliberate, documented tradeoffs for a prototype — which they reasonably were, for a five-day prototype. The mistake was not making them; it was that the document declaring them a considered tradeoff was never revisited once they stopped being true (Section 4 covers this specifically — it is still stale, today, in the current repository).

There was also a parallel, abandoned attempt at engineering scaffolding in this window: `fe57f86` and `7dc7d4e`, on a branch that forked off the very first commit and was never merged, added GitHub Actions CI, `CONTEXT.md`, four ADRs, and an agent-config layout. None of it reached `main`. **This repository has never had CI, at any point in its 33-commit history.** Section 4 returns to this; it is the single highest-leverage process gap this retrospective found.

### Phase 1 — Foundation, corrected (2026-08-27, 1 commit: `3aaf063`)

The commit subject line is itself the retrospective for this phase, and it's worth reading verbatim: *"foundation corrected - Alembic 4 zero drift, RLS wep_app + SystemSessionLocal 2 bugs, GQS 40 vs 94.29, extra=ignore top-level vs forbid WorkUnit, orphan via GQS arithmetic, file upload + sha256 NOT built, legacy global key NOT removed, HONESTY.md + 2 regression guards - Docker Desktop infra sailor-ingest.sock failure, pure-Python tests green, Postgres verification pending infra."*

Unpacked: this is the commit that introduced Alembic (retiring `create_all()`), introduced Postgres Row-Level Security with a non-superuser application role (`wep_app`) and a superuser system role (`wep`/`SystemSessionLocal`) for the handful of legitimately cross-tenant operations, found and fixed two RLS/connection-pool bugs in the process, and — critically — introduced `docs/HONESTY.md` as a first-class artifact: a running ledger of what's real versus specified-but-not-built, updated in the same commit as the feature that changes the answer. Every phase from here on inherits that discipline and, with rare lapses (Section 4), keeps it.

This is also the first appearance of the **freeze-list pattern** that shapes every subsequent commit: an explicit, named list of files/modules a given change is not allowed to touch (`gqs.py` weights, `verdict.py`, the RLS policy set, the parser). It shows up in nearly every commit message from here forward, phrased as "Must not touch: ..." It is a cheap, high-value discipline: it turns "did this change stay in scope" from a judgment call during review into a mechanically checkable claim in the commit message itself.

### Phase 2 — Ingest hardening: Slice 1a–1c (2026-08-27, 3 commits)

`47b8c54` → `4fb12d3` → `da9b84c`. Built the file-upload path (server-computed SHA-256, not caller-supplied), a pure-Python format classifier with no LLM (Levenshtein-based header matching, `ReviewQueueItem` for anything it can't confidently classify — never a guess), and the "Track A" deterministic column-to-attribute mapper, plus orphan-dependency visibility (an unresolved `dependencies[]` reference becomes a queued review item, not a silent skip). Two real, shipped bugs were caught and fixed in this window, not in a later "bug bash": uploaded file bytes were never actually persisted (only the hash was), and `GenomeVersion.gqs_score` / `ReviewQueueItem.confidence` were typed `Integer` in a system that computes floats — every stored score was silently truncated (94.29 stored as 94) until this phase's tests caught it live.

Each of these three commits ends with an honest, measured GQS number for its own test data (83.33, below the gate, for a 3-row batch that structurally loses a third of its completeness score) rather than a hardcoded expectation — a habit worth naming on its own: **assert what the code actually returns, not what you expect it to return**, especially for a scoring function whose whole job is to be sensitive to small inputs.

### Phase 3 — Progressive disclosure and ratification: Slice 2a–2c (2026-08-28, 4 commits)

`b97bc94` → `e4f056f` → `23fee33` → `248db99`. Built the read-side drill-down over a genome (business objects, then their work units, then full 18-attribute detail), partial (business-object-scoped or work-unit-scoped) ratification with audit logging, and the Automation Index — hours current/saveable computed *only* from fields actually present (never imputed), plus two graph-edge detectors (`shared_object`, `shared_resource`) that run idempotently on every read. The detector constants (a >3-unit, >6-hours/day bus-factor threshold) are explicitly called out in the commit as "the published planning constants, not invented" — a small habit that pays off later: a reviewer, or a future session, can trace every magic number back to a source document instead of having to trust that it was reasoned about once and is still right.

### Phase 4 — Multi-tenant security: Slice 3a–3c (2026-08-28 → 08-29, 6 commits)

`621dfd1` → `92f304a` → `f48eb0d` → `0b18077` → `e67e499` → `5348cc4`. Retired a single shared secret (with a hardcoded insecure default, `dev-spec-key-change-me`) in favor of per-tenant API keys hashed at rest, with a rotation grace window so an in-flight caller isn't cut off mid-rotation. Added an HTTP-level RLS test matrix (real Postgres, two tenants, proving A cannot see B across every affected router) as its own commit, separate from the feature commit — replacing what had been a manual verification script. Added a consent-receipt HTTP surface and purge job.

This phase is the clearest evidence in the whole history for **why some tests need real Postgres and cannot be faked on SQLite**: Row-Level Security is a database-level behavior. A mocked or SQLite-backed test of "can tenant B see tenant A's data" tests nothing — it tests whether the *application code* remembered to add a `WHERE client_id = ?` clause, not whether the *database* would enforce the boundary if the application code forgot. This project runs two tiers of tests for exactly this reason (Section 5.1 makes this a first-class phase-1 decision for next time, not an afterthought bolted on in week two).

### Phase 5 — Scout capture: Elevated V2, PR1–4 (2026-08-30, 2 commits)

`d8e4309` → `8737354`. Built the capture side from scratch in this window: interview sessions, a live-editable Work Capture Grid, a completeness meter, and five "elevation" analysis views (a deterministic day-schedule replay, a plain-text contradiction diff between two interview types, a keyword-weighted pain heatmap, a sentence-splitting "story to structure" fallback, and "Future Preview," which routes a captured session through the *existing* genome-import pipeline rather than a parallel writer).

Two bugs were caught by **actually running the feature in a browser**, not by the pytest suite: a completeness calculation double-counting a just-flushed row, and — the second live occurrence of the exact same RLS/connection-pool bug class from Phase 1 — a post-commit relationship read landing on a different pooled connection than the one `app.current_client_id` had been `SET` on, silently returning zero rows under RLS. Section 4.3 treats this recurrence as the single most important lesson in this whole document.

The completeness formula's own commit message states its honesty stance directly, and it's worth repeating as a pattern: a dimension with no real backing field (`Knowledge Artifacts`) is returned as `computed: false`, not faked at `0%`. The same pattern reappears at the Automation Index's `reciprocal_computed: false` and, later, this document's own Section 4.6 (GQS's `dependencies: []` ambiguity) is exactly the case where that discipline was *not* applied and should have been.

### Phase 6 — Stitching the two halves together (2026-08-30, 1 commit: `0e799c4`)

Built the missing UI over an *already-live, already-tested* backend router (`genome.py`) — no new endpoints, purely a frontend gap. This is the commit that made the honest structural finding the whole demo narrative now rests on: GQS weights `Observed%` at 40% of the score, every Scout-captured unit is honestly labeled `provenance.source_type: "declared"` (interview-derived, not document-derived), so a Scout-only genome is *structurally* capped well under the 90-point gate — verified live at GQS 30 for an 8-unit, 100%-complete session. That's not a bug to route around; it's the product working as specified, and the demo says so out loud instead of hiding it.

### Phase 7 — PR merge, then demo hardening (2026-08-30 → 08-31, 7 commits)

`6699582` (merge) → `d065c0d` → `630d87d` → `9f0d73b` → `622b9e1` → `4ea967b` → `4fc15f9`. This is where a second, distinct discipline shows up for the first time: **running the actual demo end to end and fixing what a real user hits**, as opposed to what the test suite happens to cover. Every bug in this window was reachable in the documented demo path and none were caught by the (already substantial, 96–121-test) pytest suite: a cross-tenant admin endpoint rejected on RLS with no explanatory context, a genome re-import crashing mid-loop on a unique-constraint violation and leaving partial rows behind, a tenant-count query silently zeroed by RLS, a frontend hook that never sent the auth header it needed. None of these are exotic; all of them are the specific, boring failure mode of "the thing that works when you construct the test fixture by hand doesn't work when a real click-path constructs the request" — see Section 4.2.

### Phase 8 — LLM integration and friction removal (2026-08-31, 1 commit: `a4d74f4`)

Wired a real Anthropic client behind `Story to Structure`, with one hard guarantee enforced in code, not documentation: every span the model returns is checked against the source transcript and *discarded* if it isn't a literal substring — a model that paraphrases cannot put invented words in an interviewee's mouth. Also removed the last of the demo's manual friction: one button that seeds both tenants, mints both tenants' keys, and signs the browser in, replacing a runbook of curl commands and manually copy-pasted 32-character secrets.

### Phase 9 — Full re-verification and honest defect-finding (2026-08-31 → 09-01, this session's own final stretch, 3 commits)

`f5a2ad3` → `93aadb7` → `9a9752d` → `95fc4f0`. Asked to "recheck everything," this phase did not re-run the existing tests and call it done — it reset to a genuinely empty database, re-ran migrations from zero, and found four real defects that every prior "140 tests pass" claim had never surfaced: a UI displaying the wrong one of two numbers an entity carries (global primary key vs. tenant-scoped sequence — the first genome a fresh tenant imports announced itself as "v27"), five analysis routers silently non-deterministic under connection pooling, a documented setup procedure that failed if followed in the order it was written, and — found only by *looking at a rendered chart and noticing it looked wrong*, not by any automated check — four pairs of work units in the flagship demo genome asserting mutually contradictory process order. Section 4.4 and 4.5 are both about defects from this exact phase, because they're the clearest evidence in the whole repository for why "the tests pass" and "this is correct" are different claims.

## 3. What worked — extract these as principles, not as this-project trivia

**3.1 — The freeze list.** Every slice's commit message names, explicitly, what it will not touch (`gqs.py` weights, `verdict.py`, the parser, RLS policy rewrites). This is cheap to write and expensive to violate accidentally, because a reviewer (human or AI) can check the diff against the stated scope in seconds. It also protects against a specific, real failure mode of AI-assisted development: an agent asked to add a feature will, left unconstrained, sometimes "helpfully" adjust an adjacent scoring formula or validation rule it judges to be slightly wrong. A freeze list makes that a rule violation instead of a judgment call.

**3.2 — A living honesty ledger, updated in the same commit as the code.** `docs/HONESTY.md` is not a status report written after the fact; nearly every feature commit in this history edits it in the same diff, stating precisely which claim moved from "specified" to "enforced," and — just as importantly — naming what still isn't built rather than letting the reader assume it is. The discipline that makes this work is narrow and mechanical: *never claim a capability exists without a passing test that would fail if it didn't.* That's enforceable; "be honest" on its own is not.

**3.3 — Two tiers of test, chosen for what each can actually prove.** Fast, in-memory SQLite tests for pure logic (GQS arithmetic, VERDICT gates, the classifier). Real Postgres, skip-if-unreachable tests for anything that depends on database-enforced behavior — Row-Level Security chief among them, because RLS is a property of the database, not the application, and no amount of mocking can test whether Postgres would actually block a cross-tenant query. The project is explicit that a green run with the Postgres tier skipped (`pg_skip`) is not the same claim as a green run with it executed — and burned itself once (Section 4.1) on exactly that gap.

**3.4 — Verify a fix by watching it fail first.** Repeated verbatim across many commits: "N new tests, each verified to fail against the previous code." This is the single cheapest insurance against a regression test that silently tests nothing (a common failure mode when a test and its fix are written by the same hand in the same sitting) — stash the fix, run the new test, confirm red, restore the fix, confirm green.

**3.5 — Browser verification is a distinct discipline from unit testing, and this project treats it as one.** Several of the highest-value bugs in this history (Sections 2.5, 2.7, 2.9) were found only by driving the real UI against a live backend — a stale connection-pool row, a missing auth header, a chart that renders technically-correct-but-visually-wrong data — none of which a well-designed unit test would have caught, because the bug lived in the seam between two correct components. The tool used throughout is Playwright driven headlessly, with an explicit console-error and HTTP-error check on every run, not just a visual screenshot a human has to notice something wrong in.

**3.6 — Frozen modules as an explicit contract, not a tribal norm.** `gqs.py` and `verdict.py` are both short (≈170 and ≈130 lines), both carry a docstring stating plainly that they encode a specific document's formula and are not to be adjusted without that document changing, and both are named explicitly in nearly every other commit's "must not touch" list. Freezing the two pieces of code with the most product-level consequence (they decide whether a genome passes the gate, and what autonomy level a unit gets) turned out to be exactly the right two things to protect — everything else in this codebase changed substantially over 33 commits; these two files did not.

**3.7 — Small, single-purpose migrations, checked for drift on every run.** Ten Alembic migrations across the whole history, each doing one thing (add a table, add a column, flip an enum's underlying type), with `alembic check` — "no schema drift between models and the migration chain" — run as part of the standard verification loop, not occasionally. This is what made the "reset to zero, migrate, verify" pattern in Phase 9 possible at all; a schema with drift, or one still relying on `create_all()`, cannot be reset to zero and trusted.

## 4. What went wrong — named specifically, with the evidence, because a vague lesson doesn't transfer

**4.1 — This repository has never had CI.** Not "CI regressed" — it never existed on the branch that shipped. A CI workflow was authored once (`7dc7d4e`, 2026-08-22) on a branch that forked at the very first commit and was never merged; every verification claim in every one of the other 32 commits — "140 tests pass," "typecheck clean," "zero console errors" — was produced by a human or an agent manually running the commands and reporting the result, with nothing structurally preventing a session with less discipline from skipping that step, or from merging on a red run because nothing would refuse the merge. For a project whose entire engineering culture is built on "verify, then claim" (Section 3.2–3.4), the absence of an automated enforcer of that exact culture is the single largest gap this retrospective found. It costs nothing to fix and should be the second thing V9 does (Section 5.0), after choosing where the code lives.

**4.2 — "Tests pass" and "the demo works" are different claims, and the gap between them produced most of the bugs in Phase 7 and Phase 9.** Every one of those bugs was reachable by a real user following the documented path, and none were caught by a substantial, passing pytest suite, because the suite's fixtures constructed valid state directly rather than exercising it the way a click-path does (a freshly-issued key that had never been used to hit a given endpoint before; a database with zero prior imports rather than one seeded by a previous test's leftover fixture; a chart rendered with real, messy, non-synthetic data instead of a hand-built three-node graph). The fix that worked, repeatedly, was not "write more unit tests" — it was periodically resetting to a genuinely empty environment and walking the real user-facing path end to end, with an automated pass/fail check (console errors, HTTP status codes) rather than a human eyeballing a screenshot. This should be a scheduled, not incidental, activity in V9 (Section 5.8).

**4.3 — The same bug class recurred at least three times across independent phases, and was only named as one pattern in this document, not when it happened the second or third time.** Postgres `SET app.current_client_id = ...` binds a *connection*, not a *transaction* or a *request*; a connection pool hands out connections regardless of which tenant last used them; and `db.commit()` returns a connection to the pool. Any code that reads from the database again after a commit — a `db.refresh()`, a lazy-loaded relationship access, a second query in the same request — risks running on a different pooled connection than the one the tenant binding was set on, and gets back either nothing (RLS filters everything) or, worse, another tenant's rows. This bit the project at foundation time (Phase 1), again in Scout's completeness calculation (Phase 5), and a close cousin of it (a route with no tenant binding at all, so it ran on *whatever* the pooled connection was last carrying) was the root cause of the Phase 9 "Projections shows zero for a tenant with data" bug. **A pattern that recurs three times independently is not three bugs — it's one architectural hazard that should have been solved once, centrally, and then simply couldn't be gotten wrong**, e.g. by a session-scoped context manager that re-applies the binding after every commit automatically, rather than a documented convention (`_rebind_tenant()`) that each new call site has to remember to invoke. V9 should solve this at the connection-management layer on day one (Section 5.1), not as a per-call-site discipline.

**4.4 — Migrations were run under a role that didn't own the schema, and the failure mode was maximally confusing.** The application's runtime database role (`wep_app`) is deliberately a non-superuser bound by Row-Level Security policies — correct, and necessary for RLS to mean anything. But Alembic was configured to connect using that same runtime URL, so `alembic upgrade head` on any database that had already reached the RLS migration failed with `must be owner of table work_edges` — an error that says nothing about roles or migrations to someone reading it cold, and that came *after* the point where the codebase had removed its schema-on-boot fallback, so there was no way to stand up a working database by any documented path. This was caught only in Phase 9, days after it was introduced, by a user actually trying to run the setup instructions as written. **The lesson isn't "test the docs" as a vague aspiration — it's that the CI this project never had (Section 4.1) would have caught this specific failure on commit day**, because "migrate a fresh database, then run the app" is exactly the kind of thing a CI job does before a human ever tries it by hand.

**4.5 — The flagship demo data contained a logical contradiction that nothing checked for, because nothing was built to check for it.** The sample genome shipped as the "this is what a passing, document-backed genome looks like" example declared four pairs of work units where each named the other as a dependency — under the system's own definition ("B cannot start until A completes"), a contradiction. GQS's quality gate checks for *unresolvable* dependency references (an id that doesn't exist in the batch) but never checked for *cyclic* ones, so the contradictory data scored 94.29 and cleared the 90-point gate without complaint for the project's entire history, until a rendered graph looked visibly wrong to a human and someone traced it back. **A quality gate that validates "the referenced units exist" but not "the graph they form is acyclic" is validating syntax, not the semantic claim the data is making.** This is worth generalizing: any validation layer for a directed relationship (dependency, sequence, precedence) should include a cycle check as a first-class rule, not an afterthought discovered by eyeballing a chart.

**4.6 — The quality gate's completeness metric cannot distinguish "this field is correctly empty" from "this field is missing," and that ambiguity has a real, measurable cost.** `gqs.py`'s completeness check treats an empty `dependencies: []` as a missing attribute unconditionally — correct for a mid-process unit that really does depend on something and simply wasn't given it, wrong for a genuine chain root, which by definition has no in-genome predecessor. Fixing the Section 4.5 cyclic-dependency bug left one unit as a legitimate root with an empty dependency list, and that alone cost the sample genome 1.43 points off its GQS score (94.29 → 92.86) — for having *correct*, not incomplete, data. The codebase already has the right pattern for this exact ambiguity elsewhere (Scout's completeness dimensions report `computed: false` rather than faking a `0%` for a dimension with no backing field) — it simply wasn't applied to this specific field. V9's quality-gate design should decide, deliberately, whether "no dependency" and "unknown dependency" need to be distinguishable in the schema (e.g. an explicit `is_root: true` rather than relying on emptiness to mean two different things), rather than inheriting the ambiguity by default.

**4.7 — Architecture and status documents rot silently, and a stale one is worse than no document at all.** `ARCHITECTURE.md`, written at the end of Phase 0, states as current facts things that have been false since Phase 1: "No Alembic. Schema is create-on-boot," "No app-user auth yet," and lists Alembic and per-user auth under "What is intentionally unfinished" — both have been built and load-bearing for the entire rest of the project's history. `docs/STATUS.md`, dated 2026-08-25, describes a product with no Scout, no LLM integration, no multi-tenant keys, and "customer-ready: not yet... no auth, schema is create_all" — a snapshot of a system that no longer exists, still sitting in the repository under a filename (`STATUS.md`) that reads as current. Neither document was maliciously left wrong; both were simply never revisited once the ground truth moved, while `docs/HONESTY.md` and `docs/API.md`, sitting right next to them, were updated in nearly every single commit. **The difference wasn't discipline in general — it was that HONESTY.md and API.md had an explicit, stated rule ("update this file in the same PR any time a row moves from specified to enforced") and the other two didn't.** A status document without an update trigger is a historical artifact wearing a current-tense filename; it should either be deleted, dated and archived explicitly, or given the same binding update rule the living docs have. V9 should pick exactly one of those three outcomes for every document it creates, on the day it creates it.

**4.8 — A previously-fixed class of hardcoded-secret-default bug reappeared in an unaudited corner.** Slice 3 explicitly retired a hardcoded default (`dev-spec-key-change-me`) for the legacy API secret, with a test asserting the setting no longer exists at all. `pii_encryption_key`, the symmetric key used for field-level PII encryption, ships the same shape of default (`"dev-pii-key-change-me"`) today, is used directly by `services/pii.py` with no runtime check that it's been overridden, and isn't even mentioned in `.env.example` to prompt a developer to change it. **Finding and removing one instance of a bug class doesn't mean the class is gone — a project should grep for the pattern (`.*-change-me`, hardcoded defaults on anything named `*_key`/`*_secret`) as a standing check, not rely on remembering to look everywhere the pattern could recur.** This is exactly the kind of thing a CI-run secret-scan step (Section 4.1) would catch mechanically and a one-time manual pass will not, reliably, catch twice. **Fixed, after this was written**: `pii_encryption_key` has no default at all now (the app refuses to start without `PII_ENCRYPTION_KEY` set), and `.github/workflows/ci.yml` (Section 4.1's own ask) exists — see `docs/HONESTY.md`'s "Track 2" entry for both.

## 5. Building V9 from an empty repository — a phase plan with entry/exit criteria

This section takes Sections 3 and 4 and turns them into an ordered plan, written the way a runbook should be: each phase names what must be true before it starts (entry) and what must be true before the next one starts (exit). This is deliberately more front-loaded on infrastructure than the actual V8 build was — that's the single biggest thing this document recommends changing, and it's argued for directly in 4.1–4.4.

### Phase 0 — Environment and guardrails (before any product code)

**Entry:** an empty repository and a decision on hosting (this repo, a fresh one — see the state document's own open question) and on stack (there is no strong argument in this retrospective for changing FastAPI + SQLAlchemy + Postgres + React; the friction found was entirely in *how* those tools were used, not in the tools themselves).

**Build:**
- CI on the first or second commit, not the fortieth: run backend tests, frontend typecheck+build, and `alembic check` on every push. This is the single highest-leverage line item in this whole document (4.1).
- A secret-scanning step in that same CI job — grep for hardcoded default secrets matching common naming patterns (`*_key`, `*_secret`, `*password*`) and for literal API-key-shaped strings. Catches the class of bug in 4.8 mechanically, going forward.
- Multi-tenancy and Row-Level Security decided and implemented *before* the first feature table, not retrofitted (this project's Phase 1 was, in effect, a retrofit — it worked, but cost an entire day of foundation-correction that a from-scratch build doesn't need to pay). Decide the tenant column name once (`client_id`, in this project — whatever it's called, decide it in Phase 0 and never introduce a second name for the same concept later).
- Solve the connection-pool/RLS-binding hazard (4.3) *centrally*, once: a session factory or context manager that re-applies the tenant binding after every commit automatically, so no future call site can forget to. This is worth real design time up front — it was the single most expensive recurring bug in the actual build.
- Alembic from commit one, migrating as a role that actually owns the schema (a superuser or schema-owner connection string, distinct from the RLS-bound application role) — decide and document this role split in Phase 0 so it can never again be the kind of confusing failure described in 4.4.

**Exit:** a CI-green "hello world" — one migrated table, one RLS policy, one passing cross-tenant isolation test, one passing frontend build — before any domain modeling begins.

### Phase 1 — The core primitive and its quality gate

**Entry:** Phase 0's CI is green and enforced (a PR cannot merge red).

**Build:** the domain's central object (Work Unit, or whatever V9's equivalent is) and whatever quality/validation gate decides if an instance of it is trustworthy (GQS, or its successor). Freeze this module's formula from the day it's written — name it explicitly in every subsequent commit's scope, the way `gqs.py` and `verdict.py` were (3.6). Build the gate's validation to include structural checks on any directed relationship it accepts (a cycle check for anything shaped like a dependency graph — 4.5), not only existence checks. Decide, explicitly, how the schema represents "correctly empty" versus "missing" for any optional-but-meaningful field (4.6) rather than defaulting to letting emptiness mean both.

**Exit:** the gate has a test suite that asserts real, computed numbers (never a hardcoded expected score — 3.4 (Phase 2 evidence)) against both a passing and a deliberately-blocked example, and a documented, versioned formula that a reader can trace to its source.

### Phase 2 — Ingest, with validation before writes

**Entry:** Phase 1's primitive and gate exist and are tested.

**Build:** whatever brings real data in (file upload, bulk import, an API payload). Validate everything that could collide with a database constraint — uniqueness, existence, cyclicity — in a pre-pass, before any row is written, and make the write phase one rollback boundary so a rejected batch leaves nothing behind (this project's Phase 7 fixed exactly this failure mode after it had already shipped and been hit; building the pre-pass discipline in from the start avoids the whole class).

**Exit:** an import of malformed data produces a structured, itemized rejection with zero partial writes, proven by a test that first confirms the *old* naive behavior would have left partial rows (3.4's discipline, applied here specifically).

### Phase 3 — Read-side projections

**Entry:** Phase 1–2 producing real, validated records.

**Build:** the views over those records — inventory, graph, verification contracts, allocation, economics, or whatever V9's equivalent set is. Keep these as pure projections of the same underlying records (this project's C3 principle), not a second write path. Decide the auth posture for each route deliberately and once — which routes are tenant-scoped-and-authenticated versus intentionally open — and if any route is intentionally open but still runs against a tenant-partitioned database, give it the same "bind the tenant when identified, stay open otherwise" pattern this project built in Phase 9, from the start rather than as a retrofit.

**Exit:** every projection endpoint has a test that seeds two tenants and asserts each sees only its own data — the HTTP-level RLS matrix this project didn't build until Phase 4 (Slice 3b), built here in Phase 3 instead, before there are enough routes for it to become a bigger job than it needs to be.

### Phase 4 — Scoring, allocation, and any downstream decision logic

**Entry:** Phase 1's gate and Phase 3's projections are live.

**Build:** whatever decides what happens to a validated record — autonomy scoring, cost/economics, promotion/demotion rules. Same freeze-and-document discipline as Phase 1's gate. If there's a distinction between an *authorized* level and a *recommended* one (this project's VERDICT vs. autonomy_level split), keep the write path that lowers authorization automatic and the path that raises it a deliberate human action, and encode that asymmetry in the schema, not just in application logic that could drift.

### Phase 5 — Capture / secondary intake, LLM-optional from day one

**Entry:** Phases 1–4 give the capture layer a real pipeline to feed into.

**Build:** whatever brings unstructured input in (interviews, transcripts, free text) and turns it into structured records via the *same* write path Phase 2 built, never a parallel one. If an LLM is involved anywhere, build the "no model configured" deterministic fallback and the verbatim/guardrail check *simultaneously* with the LLM path, not as an afterthought — this project got this right the first time (the substring-verification guarantee shipped in the same commit as the LLM integration, Phase 8), and it's worth calling out as the thing to repeat exactly, not just the thing to avoid getting wrong.

**Exit:** a test suite that forces the LLM-off path in every run except a small, explicitly-marked live-integration test — so the fast test suite never makes a billed network call by accident (this project's `conftest.py` fixture, built after discovering it the hard way; build it before that happens).

### Phase 6 — Demo/onboarding UX, as a first-class deliverable, not a wrapper around the API

**Entry:** the product does something real end to end via the API.

**Build:** one-command environment setup (seed data, credentials, sign-in) from the start. This project spent multiple entire commits (Phase 7–8) removing friction that a first-class "make the demo one click" requirement from day one would have prevented from existing — a runbook of curl commands, hand-computed secrets, a credential shown once with no recovery path. Decide the credential-recovery story (what happens when a demo key is lost) *before* shipping the first version of credential issuance, not after someone hits the dead end.

### Phase 7 — Design pass

**Entry:** the product's information architecture is settled (routes, nav, the shape of every screen).

**Build:** the actual visual/interaction layer. Worth sequencing this deliberately *after* the functional phases rather than alongside them — this project's UI went through one substantial, coherent rework (Phase 7) once the product's shape had stabilized, which is cheaper than reworking a UI that was built screen-by-screen against a still-moving backend.

### Phase 8 — Continuous adversarial re-verification (a standing practice, not a phase that ends)

**Entry:** the product is demoable.

**Build, ongoing:** periodically — not just before a demo — reset to a genuinely empty environment, re-run every migration from zero, and walk the real user-facing path end to end with an automated (not eyeballed) pass/fail check. This project's highest-value bug-finding sessions were exactly this activity (Phase 9), and it should be scheduled as a recurring practice from the start rather than something that happens only when someone explicitly asks to "recheck everything." A CI job that does a subset of this on every merge (Phase 0) reduces how often the manual, deeper version is needed, but does not replace it — CI proves the tests pass; only actually using the product proves the tests were testing the right thing (4.2).

## 6. Tool orchestration — Cursor, Grok, and Claude Code

This section is opinion, clearly labeled as such, informed by two things: what actually happened in *this* repository's git history (real evidence, not speculation), and general reasoning about each tool's design center of gravity (less certain, especially for Grok, which this retrospective has no direct evidence about from this codebase).

**What actually happened here.** The first five commits (`53d5d2d` through `44af43f`) are Cursor-authored (`Co-authored-by: Cursor <cursoragent@cursor.com>`) and did exactly what Cursor is built for: fast, IDE-native, visually-iterated scaffolding — take a written spec and a blank editor and produce a runnable thing quickly, with a human in the loop clicking through the UI as it takes shape. Every commit after that — the entire foundation correction, all four security/RLS phases, both Scout builds, the demo hardening, the final re-verification — is Claude Code, working in long, autonomous, test-gated sessions with adversarial self-verification as the default mode (run it, try to break it, prove the fix by watching it fail first) rather than a human eyeballing each change. The handoff point is visible in the commit log itself: the moment the project needed *provable* correctness under concurrency, multi-tenancy, and security constraints — properties that are cheap to get subtly wrong and expensive to verify by eye — is the exact moment the tooling changed.

**The recommended split, and why.**

- **Claude Code (or an equivalent long-running, tool-using agent) owns anything where correctness has to be *proven*, not eyeballed:** the data model, migrations, RLS/multi-tenancy, the quality-gate and scoring logic, the ingest/validation pipeline, and any adversarial re-verification pass. This is the mode that benefits most from running its own test suite, spawning its own Postgres to test RLS against, driving its own headless browser, and reading its own error output in a loop — all things this retrospective's evidence shows mattered directly (Sections 3.3–3.5). It is also the mode best suited to holding a large amount of cross-cutting context at once (a freeze list spanning a dozen files, an honesty ledger that has to stay consistent with a hundred-plus tests) without a human having to hold it instead.
- **Cursor (or an equivalent fast, visual, IDE-native tool) owns anything where the feedback loop is "does this look and feel right," and a human is going to be looking at every change as it happens:** initial scaffolding from a spec, UI/visual polish passes once the functional shape is settled (this project's own Phase 7), and rapid one-off exploration where getting *a* answer fast matters more than getting *the* answer provably. Its comparative advantage is tight IDE integration and human-in-the-loop speed, not autonomous multi-hour verification loops — use it where a human wants to watch and steer continuously, not where the goal is "go verify this is correct and come back."
- **Grok** — this retrospective has no direct evidence from this codebase about where it fits, so treat this as the most speculative part of this section, worth pressure-testing rather than trusting outright: it's a plausible fit for the same class of work as an independent second reviewer — a fresh, differently-biased pass over an already-built feature (a second code review, an independent audit of a claimed-honest doc against the code, a "does this argument actually hold together" pass over a spec document like V8's own 1,064-line argument) — precisely because it hasn't seen the building session's own assumptions and can catch what a tool that built the thing might rationalize past. Whether that's actually Grok's strength, versus e.g. its speed or its own tool-use design, is worth the user's own judgment more than mine here.

**A concrete workflow.** For a V9 built this way: (1) Cursor stands up the initial scaffold from the written spec, fast, with a human watching it come together — this is Phase 0/1's boilerplate, not its RLS design. (2) Claude Code takes over for every phase in Section 5 that has an explicit exit criterion involving a test or a re-verification pass — which is nearly all of them — working in the slice-and-freeze-list discipline Section 3 describes, each slice ending in a commit that states, verifiably, what changed and what was proven. (3) Before anything gets called "done" — not just before a demo — hand the diff, or the relevant living doc, to a fresh Grok session with no prior context and ask it to find what's wrong or what doesn't hold together, the same adversarial role this project's own Playwright drivers played for behavior, applied to reasoning and prose instead of runtime behavior. (4) Cursor comes back in for the design pass (Phase 7) once the shape has stabilized, and again for any future one-off exploration where speed matters more than provability.

**The single most important rule, regardless of which tool is doing the work:** never let "the tool said it's done" substitute for "I watched it prove that it's done." Every tool in this workflow — Cursor, Grok, Claude Code, this document's own author included — is capable of confidently asserting something is correct without having actually verified it. The discipline that made this project's later phases trustworthy wasn't which tool was used; it was the standing rule that a claim of correctness needs a test that would fail without the fix, run and observed to fail, before the claim gets made. Build that rule into CI (Section 5, Phase 0) so it doesn't depend on any one session, human or AI, remembering to apply it.

## 7. Pre-flight checklist for starting V9

A one-page version of Section 5, for the day work actually starts:

- [ ] Repository location decided (fresh vs. this one) and CI configured before the second commit.
- [ ] Tenant column name decided once; RLS policy pattern and role split (application role vs. schema-owning migration role) designed before the first feature table.
- [ ] Connection-pool/tenant-binding hazard (4.3) solved centrally in the session-management layer, not left as a per-call-site convention.
- [ ] Secret-scanning + hardcoded-default-detection wired into CI from day one (4.1, 4.8).
- [ ] The core primitive's quality/validation gate frozen and documented from the commit it's introduced in; cycle-checking built into any directed-relationship validation from the start (4.5); "correctly empty vs. missing" decided explicitly for every optional field that matters to scoring (4.6).
- [ ] Every living document that will exist gets an explicit update rule stated inside it on the day it's created (4.7) — or isn't created as a "status" document at all.
- [ ] Ingest validates in a pre-pass with one rollback boundary, before the first write path exists (Phase 2).
- [ ] LLM integration, if any, ships its "no model configured" fallback and its factual-guardrail check in the same commit as the model call, and tests force the model off by default (Phase 5).
- [ ] One-command demo/environment setup is a Phase-0-adjacent requirement, not a retrofit after friction is reported.
- [ ] A recurring (not incident-triggered) practice of resetting to empty and re-verifying the real user path end to end, automated pass/fail, not eyeballed — scheduled from the start, and treated as complementary to CI, not replaced by it.
